## 3. Important platform limitation

Pinterest native RSS auto-publish is event/poll driven, not an exact-time scheduler. Pinterest documentation says new feed content is normally added within 24 hours, oldest first, up to 200 Pins/day. It does not offer an RSS setting to guarantee exactly three Pins at exact times. Therefore our system can strictly control when an item first becomes visible in RSS and cap releases to three per day, but cannot guarantee Pinterest publishes each one at the precise release minute. Pinterest may batch or delay ingestion.

## 4. Recommended free design

Use a controlled release queue in the existing repository and preserve Pinterest's native RSS publisher:

1. A queue/manifest stores each guide slug, target board, stable canonical GUID, approved status, scheduled release slot, and state (queued/released/confirmed where evidence exists).
2. A scheduled GitHub Actions workflow runs at 07:00, 12:00 and 17:00 UTC. It selects at most one due guide per slot, globally capped at three/day, and never releases a slug/GUID already marked released.
3. The build publishes the scheduled feed state to Cloudflare Pages. Each board-specific RSS keeps the same URL and only exposes items that have reached their release slot, while retaining previously released items with stable GUIDs so RSS clients can deduplicate correctly.
4. A lock/concurrency guard prevents overlapping runs. The workflow validates the publication gate, image existence/dimensions, board membership, stable GUID uniqueness, per-day cap and no accidental release of unapproved guides.
5. Failures do not advance the queue. Retries are idempotent. A machine-readable run log records slot, slug, board, commit, deployment marker and result.
6. Pinterest continues to ingest RSS without API credentials or a paid scheduler. Metricool remains optional for analytics only.

## 5. Deployment implementation choice — evaluate before coding

Two implementation paths exist:

**A. Scheduled manifest commits + normal Pages deployment (simplest initial path):**
- Each successful slot updates a small machine-readable release manifest on `main`.
- Normal CI and Cloudflare Pages deployment publish the updated RSS.
- Pros: fits current static Astro architecture; no new Cloudflare product or API credentials.
- Cons: three production commits/deployments per day; full build-check runs for each state change; GitHub scheduled jobs can be delayed; Pages build quota/latency must be monitored. The commit workflow needs tightly scoped `contents: write` permission and safe conflict handling.

**B. Dynamic RSS via Cloudflare Pages Functions plus free KV/D1 state (less main-branch churn):**
- Runtime function calculates which scheduled items are visible and reads a durable release state.
- Requires introducing and testing Pages Functions, a free state store, binding/configuration and authenticated update path. Current repository has no `functions/`, Wrangler config, KV/D1 binding or Pages Functions test harness.
- More architectural complexity and more secrets/configuration; not the first choice until A proves too costly or unreliable.

Do not use direct Pinterest API posting as the first option: it adds OAuth/app setup and account/API permissions and is unnecessary while native RSS is available. Do not rely on CSV as it needs manual preparation/operation.

## 6. Critical bootstrap safeguard — existing 25 entries

Do not immediately hide or reorder the current 25 RSS entries. Pinterest's ingestion state is not fully reconciled:
- Metricool returned 29 Pin IDs (25 on 19 Nov and 4 on 21 Nov), 24 unique titles and several repeated title pairs.
- Travel & Tech board screenshot shows 7 Pins, but this alone does not establish publication state for all five boards.
- The exact Pinterest per-board status of every feed GUID is not known.

Before enabling the release gate, create a read-only bootstrap inventory of the 25 existing feed GUIDs against Pinterest board history. Mark entries already published/ingested as legacy/released. Do not re-release them. Decide explicitly what to do with any still-missing existing entries; never silently remove them from RSS or assume Pinterest has consumed them. The new 3/day cadence should initially govern future approved guides, after bootstrap reconciliation.

## 7. No new paid costs

- GitHub Actions on this public repository and Cloudflare Pages Free are candidate existing free infrastructure. Check current usage/quota and Pages build count before enabling three daily deployments.
- Do not add a paid scheduler, Metricool subscription, third-party automation SaaS, paid API or AI generation call.
- The 3/day cap is a release cap, not a guarantee of three Pinterest publications per day because Pinterest controls polling/processing.

## 9. Rollback

Disable the scheduled workflow first. Preserve the current five feed URLs and Pinterest-side RSS mappings. Restore the prior full-feed output if needed. Never delete already published Pins or clear the idempotency ledger as a rollback shortcut.
